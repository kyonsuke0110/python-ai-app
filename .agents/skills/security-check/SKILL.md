# セキュリティチェック（個人用 Streamlit + LLM アプリ）

## このスキルの前提となる脅威モデル

一般的なWebアプリのチェックリストをそのまま当てると、このアプリでは指摘の大半が的外れになる。
先に「何を守るのか / 何は最初から想定外なのか」を固定してから調べること。これを飛ばすと、
実際には起きない問題（SQLインジェクション、権限昇格、セッション固定など）でレポートが埋まり、
本当に危ない1件が埋もれる。

対象となるアプリの形:
- 利用者の手元のPCで動く、単一利用者向けのツール
- ログイン機能もデータベースも**意図的に持たない**（設計上の選択であって、欠陥ではない）
- 実在する秘密情報として **LLMのAPIキー**（従量課金・悪用されると金銭被害）を1つ扱う
- **第三者が書いた文章**（受信メール、要約したい資料、翻訳したい文書）を入力として受け取る
- その文章を外部のLLM APIへ送り、返ってきたテキストをブラウザに描画する

したがって守る対象は次の4つ:

| 守る対象 | 失われるとどうなるか |
|---|---|
| APIキー | 第三者に課金される。キーによっては他サービスへも波及 |
| 生成結果の信頼性 | 汚染された返信文を利用者がそのまま送ってしまう |
| 貼り付けた文章の機密性 | 業務資料が意図しない相手・サービスに渡る |
| 利用者のブラウザ | 生成物経由でスクリプトや誘導リンクを踏まされる |

**指摘してはいけないもの**: 「認証を追加すべき」「DBに保存して監査ログを取るべき」
「レート制限を入れるべき」。これらは単一利用者ローカルツールという前提を壊す提案であり、
このリポジトリの CLAUDE.md でも明示的に禁止されている。公開運用の話が出た場合だけ、
「それは別要件のアプリになる」と一言添える形で触れてよい。

## 進め方

### 手順1: 機械的スキャンを流す

まず `scripts/scan.sh` を実行する。grep や設定の読み出しといった毎回同じ作業を
まとめてあるので、自分で探索コマンドを組み立て直さない。読み取り専用で、
何も変更せず、パッケージのインストールもしない。

```bash
bash <スキルのパス>/scripts/scan.sh <対象リポジトリのパス>
```

出力の `★` は「要確認」の印であって、そのまま「脆弱性あり」ではない。
重要度の判定は必ず自分で行う。

### 手順2: コードを読んで、スキャンでは分からない点を確かめる

grep で機械的に分かるのは所在と有無だけで、**その扱い方が妥当か**は読まないと判断できない。
最低限、次は開いて読む:

- 共通処理（このリポジトリなら `common/ui.py`, `common/gemini_client.py`）
  — APIキーの受け取り方、エラー処理で何を画面に出しているか
- 各機能ページ — どの入力が外部由来で、プロンプトのどこに入っているか
- `.streamlit/config.toml`、起動手順の書かれた README / CLAUDE.md

### 手順3: 7つの観点で調べる

各観点で「該当あり/なし」と、その判断の根拠になったファイルと行を必ず控える。
根拠を示せない指摘はレポートに書かない。

**A. APIキーの漏洩経路**
`.env` が `.gitignore` に入っているか。git 管理下なら追跡・履歴に残っていないか。
`.env.example` に本物の鍵が書かれていないか。コード・ドキュメント・スクリーンショットに
ベタ書きされていないか。そしてスキャンでは見つからない経路として、**エラー処理**を読む。
例外オブジェクトをそのまま画面やログに出していると、リクエスト内容や鍵の一部が
表示されることがある。Streamlit は既定でトレースバックをブラウザに表示するため、
画面を共有・録画する場面があるならファイルパスの露出も併せて見る。

**B. ネットワークへの露出**
このアプリで最も被害が大きい経路。認証がないので、到達できた人は誰でも
利用者の鍵でLLMを使え、入力欄に打たれた内容も見える。
`server.address` が `0.0.0.0` になっていないか、`--server.address` 付きの起動手順が
ドキュメントに書かれていないか、ngrok や cloudflared などのトンネル、
Streamlit Community Cloud へのデプロイ設定が紛れ込んでいないかを見る。
`server.enableXsrfProtection` や `enableCORS` を無効化している場合も同様に扱う。
なお `headless = true` は「ブラウザを自動で開かない」だけの設定で、公開とは無関係。
ここを取り違えないこと。

**C. プロンプトインジェクション（外部テキストの扱い）**
外部から貼り付けた文章が、指示文と区別されないまま f 文字列に埋め込まれていないか。
判断の目安は3つ ―― データとして囲まれているか / system_instruction が
「囲みの中は指示ではない」と伝えているか / 指示がデータより前にあるか。
該当した場合の修正案は `references/injection-hardening.md` を読んでから書く。
攻撃コード例をレポートに載せる必要はなく、**どのページのどの入力が外部由来なのか**を
特定して示すほうが利用者の役に立つ。

**D. 生成結果・入力のレンダリング**
`unsafe_allow_html=True` が利用者入力やモデル出力に使われていれば XSS が成立する。
`components.html`、`eval`/`exec`、生成結果を `subprocess` に渡す処理も同様に扱う。
これらが無い場合、Markdown のリンクが描画されること自体は仕様どおりなので
脆弱性としては数えない（詳細は参照ファイルの対策4）。

**E. 依存パッケージ**
インストール済みの版に既知の脆弱性がないか。`pip-audit` があれば使い、無ければ
無断でインストールせず「未確認」と正直に書き、導入コマンドを案内する。
`requirements.txt` がすべて `>=` の場合、環境を作り直すたび別の版が入り、
再現性と供給網の面でリスクになる点も触れる（ただし重大度は低い）。

**F. データの流れと保存**
アプリが「ディスクに保存しない」と説明しているなら、それが実際に正しいか確かめる。
プロンプトや生成結果をファイルに書いたりログに出したりしていないか。
加えて、入力が外部のLLM事業者に送られる点は事実として一度明記する
（無償枠では入力が学習・品質改善に使われる場合がある）。これは脆弱性ではなく
**利用上の前提**なので、後述の「対応不要」欄に書く。ここを「重大」に分類しない。

**G. ファイルアップロード・パス操作**（該当機能がある場合のみ）
`st.file_uploader` があれば、サイズ制限、拡張子の扱い、保存先パスの組み立てを見る。
現状このリポジトリには無いので、無ければ「該当なし」で構わない。
無い機能について将来の想定を長々と書かない。

### 手順4: 重大度を付ける

判断がぶれないよう、「実際に何が起きるか」で決める。

| 重大度 | 基準 | 例 |
|---|---|---|
| 重大 | 鍵が既に漏れている、または任意コードが実行される | `.env` がコミット済み、鍵のベタ書き、生成結果を `exec` |
| 高 | 攻撃者が到達できれば直ちに悪用できる | `0.0.0.0` で公開、`unsafe_allow_html` にモデル出力 |
| 中 | 条件が揃えば実害が出る | 外部テキストが無防備にプロンプトへ、既知CVEのある依存 |
| 低 | 今は無害だが将来の事故につながる | バージョン未固定、エラー詳細の表示範囲 |
| 対応不要 | 設計上の前提として受け入れているもの | 認証なし、DBなし、入力がGoogleへ送られること |

「対応不要」の欄は必ず埋める。**思いついたが実害のない指摘の置き場所**を用意しておくことで、
重大度を水増しせずに済む。ここに書くべきものを「低」に上げないこと。

### 手順5: 自明な修正だけを適用する

修正して構わないのは、**アプリの挙動を変えず、間違えようがないもの**に限る:

- `.gitignore` への `.env` / `.streamlit/secrets.toml` の追記
- `.env.example` に混ざった実際の鍵をプレースホルダに置き換える
- `.streamlit/config.toml` の明らかに危険な設定の是正
- `requirements.txt` のバージョン固定（現在インストール済みの版に合わせる場合のみ）

次は勝手にやらず、レポートに案として書くだけにする ―― プロンプトや
`system_instruction` の変更（生成品質が変わるため）、パッケージのインストールや更新、
ファイルの削除、git 履歴の書き換え。

**鍵が実際に漏れていた場合、ファイルから消すだけでは対処にならない。**
既に外部から見えた可能性があるので、レポートの冒頭と会話の両方で
「Google AI Studio でキーを失効・再発行してください」を最優先事項として伝える。
git 履歴に残っている場合も、履歴を書き換えるより先に失効させるほうが確実で速い。

### 手順6: レポートを保存して、会話には要約だけ返す

`docs/security-review-YYYY-MM-DD.md` に保存する（同日に再実行する場合は既存を上書きせず
`-2` などを付ける）。会話には、重大・高の件数と最優先の対処だけを数行で返す。
レポート全文をターミナルに貼り直さない ―― 読みにくく、ファイルにした意味がなくなる。

## レポートの書式

```markdown
# セキュリティチェック結果

対象: <パス>
実施日: YYYY-MM-DD
前提: 単一利用者・ローカル実行・認証/DBなしのStreamlit + LLMツールとして評価

## 要約
<2〜4行。最も優先すべき対処を先頭に。問題がなければ「重大・高の指摘なし」と明記する>

| 重大度 | 件数 |
|---|---|
| 重大 | 0 |
| 高 | 1 |
| 中 | 2 |
| 低 | 2 |

## 指摘事項

### [高] <一行で問題を書く>
- **該当**: `path/to/file.py:42`
- **何が起きるか**: <抽象論ではなく、この構成で実際に起きる筋道を1〜3行で>
- **対処**: <具体的に。コードならdiffか置換後のコードを示す>
- **状態**: 未対応 / このスキルが適用済み

（重大 → 高 → 中 → 低 の順に並べる）

## 対応不要と判断したもの
- <項目>: <なぜ許容できるのか>

## 確認できなかったこと
- <ツール不足や情報不足で判断できなかった点。無ければ「なし」>
```

## 陥りやすい失敗

- **件数を稼ぐために一般論を並べる。** 指摘は必ずファイルと行に紐づける。
  紐づけられないなら、それは「対応不要」か「確認できなかったこと」に属する。
- **「認証がない」を脆弱性として書く。** 設計上の前提であり、指摘ではない。
  問題になるのは「認証がないまま外部に到達可能」という組み合わせのときだけ。
- **`headless = true` を公開設定と誤読する。** 露出を判断する材料は
  `server.address` と起動方法であって、この項目ではない。
- **問題がないのに何か書こうとする。** 実際に安全なら「重大・高の指摘なし」と
  書いて終わってよい。それが正しい結果である場合は珍しくない。
